## 4. 关键技术决策与建议

### 4.1 缩略图加载策略

**建议**：不生成应用内缩略图，直接从系统相册原图采样加载。

- 与需求 NFR-02 一致（不存储图片文件、不生成缩略图副本）
- 使用 `BitmapFactory.Options.inSampleSize` 控制加载尺寸 ≤ 256x256
- 参考现有代码：[AudiobookLibraryScreen.kt 中的 bitmap 加载逻辑](file:///D:/codebase/tech/mpvRx/app/src/main/java/app/gyrolet/mpvrx/ui/browser/audiobooks/AudiobookLibraryScreen.kt#L1229)

### 4.2 图片查看器架构

**建议**：新建 `FrameCaptureViewerScreen`，复用 `ZoomableImage` 核心组件，但独立管理页面结构。

原因：
- 现有 `ImageViewerScreen` 面向 `NetworkFile` 和远程图片加载
- 帧捕获查看器需要不同的顶部/底部操作栏和跳转逻辑
- 两种场景差异较大，强行复用会导致代码耦合

### 4.3 数据库表设计建议

```kotlin
@Entity(tableName = "frame_captures")
data class FrameCaptureEntity(
  @PrimaryKey(autoGenerate = true) val id: Long = 0,
  val imageUri: String,          // 系统相册文件 URI
  val videoPath: String,         // 原视频路径/URL
  val videoTitle: String,        // 视频标题
  val positionMs: Long,          // 时间点（毫秒）
  val capturedAt: Long = System.currentTimeMillis(),
)
```

### 4.4 性能保障

- 网格列表使用 `LazyVerticalGrid` + `key`，确保滚动性能
- 缩略图加载控制在 IO 线程，使用 `Dispatchers.IO`
- 数据量 > 5000 时启用 Room + Paging3 分页
- 大图查看器预加载相邻图片（复用 `ImageViewerViewModel` 的 `preloadNeighbors` 模式）

## 5. 风险与缓解

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|----------|
| 系统相册文件被用户手动删除 | 中 | 中 | 列表加载时检测文件存在性，显示占位图；点击查看时提示「文件已删除，是否移除记录？」 |
| 帧捕获文件 URI 因系统更新失效 | 低 | 中 | 使用持久化 URI（`takePersistableUriPermission`）或存储相对路径 |
| 大量帧捕获导致列表卡顿 | 低 | 中 | 分页加载 + 缩略图采样 + RecyclerView 复用 |
| mpv 截图命令在特定格式下失败 | 低 | 低 | 已有 Android Fallback 机制（`captureWithAndroidFallback`） |

## 7. 总结

帧捕获与收藏功能在 mpvRx 项目中属于**中等复杂度、高复用度**的功能。项目已有截图、逐帧导航、底部导航栏、图片查看器、数据库等成熟基础设施，核心工作在于将这些模块串联并定制 UI。

**无技术难点**，主要挑战在于：
1. 帧捕获详情页的 UI 定制（顶部信息栏 + 底部操作栏）
2. 系统相册图片的缩略图加载和存在性检测
3. 跳转回视频播放时的边界情况处理

推荐按上述 4 个阶段分步实现，每阶段完成后进行功能验证，整体预计 **2 ~ 3 周**完成。
