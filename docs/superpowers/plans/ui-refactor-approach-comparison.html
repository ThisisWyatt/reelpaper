reelPaper UI 重构方案对比

可行性评估 · 三种实现路径

推荐

方案 A：分层渐进重构

主题层先行 → 组件层逐页替换 → 导航层收尾

策略

第一阶段搭建拟物主题引擎（配色、海拔系统、纸纹噪点），将「纸与朱砂」注入 ColorScheme；第二阶段按页面优先级逐个替换组件（主页→播放列表→网络→设置→弹窗表单）；第三阶段重构导航系统为悬浮纸坞。

优势
  • 每个阶段可独立验证，风险可控
  • 主题层完成后即可看到配色效果，团队反馈快
  • 组件替换期间 Material3 与拟物组件可短暂共存
  • 随时可暂停，不阻塞主线开发
劣势
  • 过渡期存在短暂的风格混搭（约 2-3 周）
  • 需要定义清晰的组件替换顺序和接口
工作量 ~120-160 工时
周期 4-6 周
风险 低

方案 B：全量一步重构

一次性替换全部组件和导航系统

策略

在一个长特性分支上同时开发主题引擎、所有自定义组件和悬浮纸坞导航，完成后一次性合并。开发期间主线继续迭代，最终通过 rebase 合入。

优势
  • 不存在风格混搭期
  • 组件设计可全局统筹，一致性最高
  • 用户感知到的变化完整、无中间态
劣势
  • 长分支与主线分歧大，rebase 冲突风险高
  • 无法阶段性验证，出问题难定位
  • 阻塞其他 UI 相关功能开发
  • 如果中途发现设计不可行，沉没成本大
工作量 ~100-140 工时
周期 3-5 周（连续）
风险 高

方案 C：双包并行

新建独立 activity/模块，两套 UI 并行运行

策略

在同一 app 内新建一套完整的拟物 UI（独立 Activity 或导航子图），通过设置中的开关切换。新旧 UI 共享同一套 ViewModel/Repository/Database 层。

优势
  • 零风险——旧 UI 完全不动
  • 可同时对比两种风格
  • 用户可选，平滑过渡
劣势
  • APK 体积显著增加（双套组件代码）
  • 维护成本翻倍——每个功能需同时改两套 UI
  • 长期共存违背「完全替换」的决策
  • 最终还是要删除旧 UI，等于多做了一遍
工作量 ~180-240 工时
周期 6-8 周
风险 低（但维护成本高）
